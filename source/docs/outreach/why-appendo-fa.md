# ‏AppEndO؛ به قدرت هوش مصنوعی افسار بزنید، فراتر از دمو بسازید

‏*یک پلتفرم یکپارچه برای ساخت و اجرای نرم‌افزار روی زیرساخت خودتان؛ تا حاصل کدنویسی با هوش مصنوعی، یک سیستم منسجم باشد، نه توده‌ای از کدهای تولیدشده.*

‏کدنویسی با هوش مصنوعی گاهی شبیه سوار شدن بر یک اسب سرکش است: قدرتش خیره‌کننده است، به‌سرعت شتاب می‌گیرد، اما درست وقتی فکر می‌کنید همه‌چیز عالی پیش می‌رود، می‌فهمید تند رفتن لزوماً به معنای در اختیار داشتن مسیر نیست.

‏از محیطی مثل Cursor بخواهید یک صفحه، یک API یا اتصال به پایگاه داده بسازد؛ ممکن است خیلی زود نتیجه بگیرید. اما اگر قرار باشد یک نرم‌افزار بزرگ، سال‌ها با نیازهای متغیر، توسعه‌دهندگان مختلف و قواعد کسب‌وکار تازه زندگی کند، ماجرا فرق می‌کند. مدل دسترسی را چه کسی تعیین می‌کند؟ کدام کتابخانهٔ رابط کاربری مبناست؟ منطق کسب‌وکار باید کجا قرار بگیرد؟ و چه چیزی جلوی این را می‌گیرد که پرامپت بعدی، بی‌سروصدا معماری دیگری به پروژه اضافه کند؟

‏مسئله کمبود کد نیست؛ مسئله، نبود تصمیم‌های مشترکی است که با تغییر بعدی از بین نروند.

‏**AppEndO به این قدرت افسار می‌زند.** برای توسعه‌دهنده و عامل هوش مصنوعی، بستری از پیش شکل‌گرفته فراهم می‌کند: اجزای قابل استفادهٔ مجدد، استانداردهای روشن، معماری قابل کشف و یک Studio برای ساخت و اجرای نرم‌افزارهای کسب‌وکار. دیگر لازم نیست با هر قابلیت تازه، از هوش مصنوعی بخواهید زیرساخت را هم از نو اختراع کند؛ از آن می‌خواهید داخل یک چارچوب مشخص کار کند.

‏فایدهٔ دوم هم کاملاً ملموس است: لازم نیست ماه‌های ابتدایی هر پروژه را دوباره صرف ساختن همان زیرساخت‌های همیشگی کنید.

## ‏یک پلتفرم، نه صرفاً یک قالب آمادهٔ دیگر

‏AppEndO یک **پلتفرم خودمیزبان برای ساخت و اجرای نرم‌افزارهای سازمانی** است: یک Studio مدیریتی، یک محیط اجرای برنامه و ابزارهایی برای ارائهٔ پرتال‌های کاربران و اپلیکیشن‌های تخصصی.

‏استک آن بر Node.js 22، Express، React، Vite و TypeScript بنا شده است. SQL Server گزینهٔ پیش‌فرض و پیشنهادی برای پایگاه دادهٔ لایهٔ مدیریتی یا control plane است؛ راهنمای نصب، PostgreSQL، MySQL و SQLite را هم ارائه می‌کند. جدول‌های جدید این لایه و محیط اجرای Data API بر Sequelize تکیه دارند؛ استفاده‌های باقی‌مانده از Prisma مربوط به بخش‌های قدیمی است، نه مسیر توسعهٔ جدید.

‏اهمیت این ترکیب در آن است که AppEndO فقط مجموعه‌ای از صفحه‌های خوش‌ظاهر نیست. مدیریت هویت، دسترسی به داده، ساخت صفحات، گردش کار، بسته‌بندی، ابزارهای هوش مصنوعی و کنترل‌های عملیاتی، در یک پلتفرم کنار هم قرار گرفته‌اند.

‏از طرف دیگر، نباید آن را یک ERP آماده فرض کرد. هسته، ابزار ساخت و محیط اجرا را فراهم می‌کند؛ برنامه‌های تخصصی هر حوزه در قالب بسته‌های اکوسیستم توسعه پیدا می‌کنند.

## ‏پروژه را مستقیم در Cursor باز کنید و همان روز توسعه را شروع کنید

‏برای کار به این شکل، به افزونهٔ خاص یا IDE اختصاصی نیازی ندارید. **پوشهٔ AppEndO را در Cursor باز کنید، پلتفرم را اجرا کنید و ساختن را شروع کنید.** سرعت را Cursor می‌آورد: ایندکس کردن کد، ویرایش هم‌زمان چند فایل، حالت‌های Agent و Plan و ترمینال یکپارچه. افسار را AppEndO می‌زند: تصمیم‌هایی که عامل Cursor باید از آن‌ها پیروی کند، به‌جای اینکه هر بار از نو اختراعشان کند.

‏به محض باز شدن پروژه، عامل Cursor این‌ها را پیش روی خود دارد:

- ‏**یک نقطهٔ شروع برای هر جلسهٔ هوش مصنوعی.** فایل [`AGENTS.md`](../../AGENTS.md) در ریشهٔ مخزن قرار دارد و Cursor آن را به‌عنوان دستورالعمل پروژه می‌خواند. این فایل ترتیب اولویت منابع، قواعد همیشه فعال (کار فقط در محدودهٔ درخواست، اولویت Base Components، گراف وابستگی ماژول‌ها، نگه‌داری JWT فقط در کوکی و مسیر دسترسی به پایگاه داده) و یک نقشهٔ موضوعی را تعیین می‌کند که به عامل می‌گوید برای هر کار، فقط کدام فایل استاندارد را بخواند.
- ‏**زمینهٔ متمرکز به‌جای شلوغی.** فایل `.cursorignore` پروژه وابستگی‌ها، خروجی بیلد، پیش‌نویس‌های زمان اجرا، اسناد بایگانی‌شده و فایل‌های رسانه‌ای حجیم را از ایندکس Cursor بیرون نگه می‌دارد تا توجه عامل روی کد و استانداردهای مهم بماند.
- ‏**نقشهٔ کد.** [ایندکس کد](../ai/CODEBASE_INDEX.md) و یادداشت‌های معماری پیش از هر جست‌وجو به عامل می‌گویند کد، فضای کاری و API هر صفحه کجاست.
- ‏**قطعه‌های آمادهٔ قابل استفادهٔ مجدد.** Base Components، CRUD Set، Server Functions، Data Studio، سیاست‌های رکورد و موتور گردش کار از قبل وجود دارند؛ پس درخواستی مثل «یک صفحهٔ تأیید درخواست اضافه کن» یعنی توسعهٔ پلتفرم، نه ساختن یک فریم‌ورک کوچک تازه.
- ‏**خودِ پلتفرم زنده به‌عنوان منبع ابزار.** AppEndO یک endpoint ورودی MCP هم دارد (`/api/mcp`، محافظت‌شده با کلید API) که بسته‌های قابلیتی فعال‌شده در تنظیمات را در دسترس می‌گذارد. کلاینت‌هایی که از MCP پشتیبانی می‌کنند، مثل Cursor، می‌توانند به آن وصل شوند تا عامل علاوه بر فایل‌های کد، با ابزارهای پلتفرم در حال اجرا هم کار کند.

‏جلسهٔ اول معمولاً ساده است: پوشه را در Cursor باز کنید، `npm install` و `npm run dev` را اجرا کنید، ویزارد نصب را در مرورگر تمام کنید و بعد اولین قابلیت واقعی‌تان را از عامل Cursor بخواهید. این عامل درون پلتفرمی کار می‌کند که کنترل دسترسی، لاگ و مدل برنامه را از قبل دارد و لازم نیست اول این بخش‌ها ساخته شوند.

‏نکتهٔ اصلی همین ترکیب است. **Cursor یک محیط کدنویسی فوق‌العاده سریع به شما می‌دهد و AppEndO به همان محیط یک زیرساخت در سطح تولید و یک دفترچهٔ قوانین روشن.** همهٔ امکانات Cursor سر جایش می‌ماند و ساختاری اضافه می‌شود که آن را در مسیر درست نگه می‌دارد.

## ‏۱. به هوش مصنوعی نقشه، زبان مشترک و مرز بدهید

‏یک عامل کدنویسی عمومی می‌تواند راه‌حلی ظاهراً قابل قبول تولید کند. محیط درست کمک می‌کند راه‌حلی تولید کند که واقعاً به این پروژه تعلق دارد.

‏AppEndO این مسئله را در دو سطح دنبال می‌کند.

### ‏در IDE؛ تصمیم‌های پروژه باید پیدا شوند، نه حدس زده شوند

‏[مرکز استانداردهای عامل‌های هوش مصنوعی](../../AGENTS.md) قواعد پایهٔ معماری و امنیت را مشخص می‌کند. به‌جای تکیه بر یک پرامپت بسیار بلند، [استانداردهای موضوعی](../standards/INDEX.md) برای حوزه‌هایی مانند صفحات CRUD، Data API، سیاست رکوردها، دیالوگ‌ها و مسیریابی وجود دارد. قواعد مسیرمحور Cursor در درخت توسعه نیز عامل را به استاندارد مربوط هدایت می‌کنند؛ قرار نیست نسخهٔ دیگری از همان قواعد را تکرار کنند. فایل‌های ویژهٔ IDE در `.cursor/` همراه نسخهٔ عمومی منتشر نمی‌شوند، اما مرکز استانداردها و مستندات در آن حضور دارند.

‏[فهرست تولیدشدهٔ کدبیس](../ai/CODEBASE_INDEX.md) نشان می‌دهد هر صفحه به کدام پوشهٔ قابلیت، فضای کاری و پیشوند API مربوط است. ابزارهای feature graph هم مسیر بررسی را محدود و هدفمند می‌کنند. قواعد قفل ویرایش صفحه می‌گویند تا وقتی درخواست کاربر صریحاً یک صفحه را هدف نگرفته است، فایل‌های آن نباید تغییر کنند؛ یک مانع آگاهانه در برابر تغییرات ناخواستهٔ «حالا که اینجا هستم، این یکی را هم درست کنم».

‏این‌ها قواعد مهندسی و کنترل رفتار عامل هستند، نه تضمین بی‌خطا بودن IDE. ارزششان در کم کردن ابهام است: کجا را بخوان، چه چیزی را دوباره استفاده کن و به چه چیزی دست نزن.

### ‏داخل پلتفرم؛ ابزارهایی که خودِ برنامه را می‌شناسند

‏AppEndO یک عامل درون‌برنامه‌ای با حالت‌های **Ask، Plan و Agent** هم دارد. این عامل با Cursor یکی نیست: Cursor محیط توسعه است؛ عامل AppEndO درون همان پلتفرم زندهٔ برنامه کار می‌کند.

‏[راهنمای کدنویسی درون‌برنامه‌ای](../standards/vibe-operator-playbook.md) مسیر مشخصی دارد: ابتدا اطلاعات مرتبط را بازیابی کن، بعد برنامه بریز، پیش‌نویس بساز و در پایان اعتبارسنجی و نهایی‌سازی کن؛ همان retrieve → plan → draft → finalize. ابزارها می‌توانند استانداردهای پروژه و زمینهٔ صفحه را بخوانند، feature graph را بررسی کنند، Server Functions را پیش‌نویس و آزمایش کنند و چیدمان Component Designer بسازند. تغییرات مدیریت‌شده از مسیر proposal/apply پلتفرم عبور می‌کنند و بازگردانی آخرین تغییر اعمال‌شده نیز در دسترس است. پیشنهاد معتبر در حالت Agent می‌تواند خودکار اعمال شود؛ بنابراین نباید وعده داد که پیش از تک‌تک تغییرات حتماً یک تأیید دستی گرفته می‌شود.

‏تابع‌ها و چیدمان‌های مدیریت‌شده پس از اعمال، روی **همان نمونهٔ در حال اجرای AppEndO** کار می‌کنند. برای پیش‌نمایش این نوع تغییر لازم نیست یک موتور اجرای جداگانه بالا بیاورید. در مقابل، بازآرایی گستردهٔ کد و اشکال‌زدایی تعاملی عمیق، همچنان جای طبیعی خود را در IDE دارند.

‏بسته‌های قابلیت MCP، عامل را به داده، استانداردها، Designer، Server Functions، کارهای پس‌زمینه، بسته‌ها، Git و عملیات گردش کار متصل می‌کنند. کنترل دسترسی MCP و محدودیت‌های اتصال به سرورهای بیرونی هم باعث می‌شوند ابزارها در چارچوب مدیریت دسترسی پلتفرم قرار بگیرند، نه اینکه یک مسیر نامحدود برای دور زدن آن باشند.

| ‏موضوع | ‏کدنویسی با هوش مصنوعی، بدون یک پلتفرم مشترک | ‏توسعه با هوش مصنوعی روی AppEndO |
| --- | --- | --- |
| ‏معماری | ‏توضیح دوباره یا کشف مجدد قراردادهای پروژه | ‏شروع از لایه‌های مستند، استانداردهای موضوعی و نقشهٔ کدبیس |
| ‏رابط‌های تکراری | ‏تولید یک پیاده‌سازی دیگر برای جدول و فرم | ‏استفادهٔ مجدد از Base Components، CRUD Set و الگوهای Designer |
| ‏دسترسی‌ها | ‏طراحی و اتصال جداگانهٔ مسیرهای اعمال مجوز | ‏توسعه بر پایهٔ کنترل دسترسی مشترک و سیاست رکوردهای پیکربندی‌شده |
| ‏محدودهٔ تغییر | ‏اتکای زیاد به دقت پرامپت | ‏قواعد هدف‌گیری صفحه و ابزارهای آگاه از ساختار پلتفرم |
| ‏تحویل قابلیت | ‏سرهم کردن زیرساخت، پیش از رسیدن به نیاز کسب‌وکار | ‏ساختن روی Studio، محیط اجرا و مدل بسته‌بندی موجود |

‏هدف، ضعیف کردن هوش مصنوعی نیست؛ **هدف این است که با هر قابلیت تازه، معماری تازه‌ای اختراع نشود.**

## ‏۲. از جایی شروع کنید که رسیدن به آن معمولاً ماه‌ها طول می‌کشد

‏بیشتر نرم‌افزارهای کسب‌وکار به مجموعه‌ای از قابلیت‌های مشترک نیاز دارند؛ همان کارهای ضروری و کم‌سروصدایی که معمولاً در معرفی محصول دیده نمی‌شوند و به همین دلیل، هزینه‌شان دست‌کم گرفته می‌شود.

‏داشتن صفحهٔ ورود، مدیریت هویت نیست. مخفی کردن یک دکمه، کنترل دسترسی نیست. ذخیرهٔ زمان آخرین تغییر، تاریخچهٔ قابل بررسی نیست. و یک دموی بی‌خطا هم هنوز به معنای داشتن برنامه‌ای برای بهره‌برداری نیست.

‏AppEndO این پایه‌ها را در اختیار پروژه می‌گذارد تا از ابتدا، تمرکز روی رفتار کسب‌وکار باشد، نه کنار هم چیدن اجزای زیرساخت.

### ‏هویت و دسترسی، فراتر از «یک لاگین هم اضافه کنیم»

‏کاربران، نقش‌ها، نشست‌های JWT در **کوکی‌های HttpOnly**، قفل ورود، مدیریت نشست‌های فعال و پروفایل‌های Individual/Company در پلتفرم وجود دارند. اتصال‌های آمادهٔ ارائه‌دهندگان هویت نیز Google، GitHub، Microsoft Entra و OIDC عمومی را پوشش می‌دهند.

‏**Function Access Control** یک مدل ACL مشترک برای بخش‌هایی مانند Server Functions، Data API، MCP، پرتال‌ها و Workbookها فراهم می‌کند. Access Assistant نیز به مدیر سیستم کمک می‌کند دسترسی صفحه و تابع را بدون ویرایش دستی ردیف‌های ACL تنظیم کند.

‏AppEndO دو پرسشی را که خیلی وقت‌ها در برنامه‌ها با هم مخلوط می‌شوند، از یکدیگر جدا می‌کند:

- ‏**Capability:** آیا این فرد اصلاً اجازه دارد این عملیات را فراخوانی کند؟
- ‏**Scope:** اگر اجازه دارد، کدام رکوردها را می‌تواند ببیند یا تغییر دهد؟

‏[Record Policy](../standards/record-policy.md) برای مدل‌های پیکربندی‌شدهٔ Data API، محدودهٔ دسترسی سطری بر اساس سازمان و جغرافیا ایجاد می‌کند. مثلاً کارشناس یک منطقه ممکن است مجوز ویرایش درخواست‌ها را داشته باشد، اما فقط درخواست‌های منطقهٔ خودش را.

‏این قابلیت به تنظیم نیاز دارد: محدودهٔ رکورد به‌صورت پیش‌فرض خاموش است و تابع سفارشی‌ای که از مسیر Data API عبور نمی‌کند، باید صریحاً این محدودیت را اعمال کند. فیلتر منطقی سطرها هم معادل جداسازی سخت‌گیرانهٔ مستأجرها نیست. این مرزها واقعیت‌های مهم مهندسی‌اند؛ نه دلیلی برای اینکه در هر پروژه یک سیستم مجوزدهی دیگر بسازیم.

### ‏داده، API و رابط کاربری که از قبل با هم جور هستند

‏**Data Studio** مدل‌های بصری Edge، رابطه‌ها، انتشار REST Data API، برگهٔ زندهٔ داده، SQL Console فقط‌خواندنی و غنی‌سازی ساختار داده با کمک هوش مصنوعی را فراهم می‌کند. منابع رابطه‌ای متصل می‌توانند SQL Server، PostgreSQL، MySQL، Oracle یا SQLite باشند.

‏برای منطق اختصاصی، **Server Functions** امکان نوشتن و نسخه‌بندی APIهای JavaScript/TypeScript را در یک محیط اجرای محدودشده و همراه با مستندات OpenAPI می‌دهند. **API Talk** هم یک کلاینت HTTP داخل Studio است؛ با مجموعهٔ درخواست‌ها، محیط‌های مختلف، بررسی نتیجه‌ها، تاریخچه و امکان وارد کردن تعریف درخواست‌ها.

‏در سمت کاربر، **Component Designer**، **Base Components** و **CRUD Set** زبان مشترکی برای ساخت صفحه، جدول، فرم و جریان‌های فهرست، ایجاد، ویرایش و حذف فراهم می‌کنند. کاتالوگ اجزا فقط به فرم محدود نیست؛ نمودار، نقشه، کانبان، ثبت امضا، اسکنر و نمایش سند هم در آن وجود دارد.

‏مزیت فقط این نیست که «جدول آماده داریم». مزیت این است که جدول، فرم، قرارداد API و رفتارهای اطرافشان می‌توانند با بزرگ شدن برنامه همچنان یکدست بمانند.

### ‏فرایند واقعی کسب‌وکار، نه صرفاً یک فیلد وضعیت

‏**Workflow Engine** بومی پلتفرم، طراح بصری، اجرای ماندگار گردش کار، وظایف انسانی و فرم انجام کار را در اختیار می‌گذارد. تخصیص کار نیز می‌تواند بر اساس نقش، کاربر مشخص، توزیع نوبتی یا کوتاه‌ترین صف انجام شود.

‏اصل تأیید دونفره یا four-eyes، ارجاع به سطح بالاتر، مدیریت غیبت، رسیدگی به کارهای ناموفق در dead-letter، زمان‌سنج‌ها، webhookها، مسیرهای موازی، زیرگردش‌ها و نگهداری رمزگذاری‌شدهٔ اسرار گردش کار، به همان نیازهایی پاسخ می‌دهند که معمولاً بعد از دموی مسیر موفق ظاهر می‌شوند. کاتالوگ عملیات نیز با بسته‌ها قابل توسعه است.

‏این امکانات برای تأیید درخواست، پذیرش و شروع همکاری، رسیدگی به پرونده و هر فرایندی مفیدند که در آن «یک نفر باید مرحلهٔ بعد را انجام بدهد» لازم است به مسئولیتی مشخص و قابل پیگیری تبدیل شود.

### ‏تاریخچه و بهره‌برداری، از همان ابتدا

‏لاگ‌های ساختاریافتهٔ برنامه و رویدادهای ممیزی احراز هویت، از **Record Event Log** جدا هستند. Record Event Log تاریخچه‌ای افزایشی از تغییرات رکوردهای تحت رهگیری نگه می‌دارد؛ با ثبت عامل تغییر، دلیل آن، کنترل پوشاندن مقادیر حساس و امکان مشاهدهٔ تاریخچه. این سازوکار event sourcing نیست؛ وضعیت فعلی رکورد همچنان مرجع اصلی است. handler سفارشی نیز باید به مسیر ثبت رویداد متصل شود؛ قرار نیست هر تغییری بدون هیچ کاری، جادویی رهگیری شود.

‏کارهای پس‌زمینه، زمان‌بندی وظایف، کش حافظه‌ای یا Redis، بررسی سلامت و آمادگی سرویس، File Manager، فضای کاری Git و Platform Transfer، بخش دیگری از نیازهای تکراری را پوشش می‌دهند. صندوق ورودی شخصی هم وظایف، بازخوردها، هشدارها و تاریخچهٔ ارسال پیام را یکجا جمع می‌کند؛ لازم نیست هر قابلیت، صف جداگانه‌ای برای جلب توجه کاربر بسازد.

‏برای تیمی که در غیر این صورت باید همهٔ این پایه‌ها را خودش بسازد و به هم متصل کند، **حذف ماه‌ها کار تکراری یک فرصت واقعی است؛ نه یک عدد اندازه‌گیری‌شده یا تضمین همگانی.** میزان صرفه‌جویی به نیاز پروژه و نقطهٔ شروع تیم بستگی دارد.

‏هدف این است که زودتر به پایه‌ای مناسب برای یک نرم‌افزار ماندگار برسید، نه اینکه یک MVP دورریختنی را سریع‌تر تحویل بدهید. بررسی امنیت، پشتیبان‌گیری، آزمون و آماده‌سازی محیط عملیاتی همچنان بر عهدهٔ تیم تحویل است.

## ‏۳. دادهٔ عملیاتی را به بینش قابل استفاده تبدیل کنید

‏خیلی از استک‌ها در CRUD متوقف می‌شوند؛ وقتی نوبت گزارش و تحلیل می‌رسد، تیم باید دنبال ابزار و زیرساخت دیگری بگردد.

‏[Pivot API](../standards/data-api-pivot.md) در AppEndO یک قرارداد مشترک درخواست و نتیجه دارد: چه داده از یک مجموعه‌دادهٔ رابطه‌ای تخت بیاید، چه از **مدل ستاره‌ای ROLAP داخلی**، چه از **پل اختیاری Microsoft SSAS برای OLAP** و چه از تجمیع فقط‌خواندنی **MongoDB** و **Elasticsearch**.

‏این اتصال‌ها عمداً یکسان معرفی نمی‌شوند: پشتیبانی تحلیلی MongoDB و Elasticsearch به معنای CRUD عمومی روی آن‌ها نیست؛ Redis گزینهٔ کش است، نه پایگاه دادهٔ تحلیلی؛ و SSAS به یک سرویس پلِ جداگانه نیاز دارد. فراهم‌کنندهٔ داخلی ROLAP نیز سرور XMLA برای اتصال ابزارهای BI بیرونی نیست.

‏صفحه‌های داشبورد از همان اجزای Designer استفاده می‌کنند. توسعه‌دهنده دامنهٔ دادهٔ مجاز را تعریف می‌کند؛ کاربر می‌تواند چیدمان را شخصی‌سازی کند و در همان محدوده، ویجت اضافه کند. فیلتر، بررسی جزئی‌تر داده‌ها، اشتراک‌گذاری، نمایش در صفحات دیگر با کنترل‌های embedding، snapshot و نظرهای مرتبط با هر ویجت، این تجربه را کامل‌تر می‌کنند.

‏دستیار اختیاری هوش مصنوعی داشبورد هم می‌تواند تنظیمات ویجت را پیش‌نویس کند یا نموداری را که همین حالا نمایش داده شده است توضیح بدهد. مرز مستند آن نکتهٔ مهمی دارد: **هوش مصنوعی، مجوز دادهٔ بیشتری از مسیر دستی همان کار به دست نمی‌آورد.**

‏در نتیجه، داشبورد فقط یک تصویر زیبا برای معرفی محصول نیست؛ بخشی از خود برنامه است که قواعد روشن داده و دسترسی بر آن حاکم است.

## ‏۴. یک زیرساخت برای سازنده، مدیر سیستم و کاربر نهایی

‏وقتی مشتری یا شریک تجاری هم باید از سیستم استفاده کند، یک پنل مدیریتی خوب فقط نیمی از ماجراست.

‏AppEndO، Studio مدیریتی و پرتال‌های کاربران را روی یک استک ارائه می‌کند. مسیریابی بر پایهٔ ترکیب فرهنگ، برنامه و مسیر، تجربه‌های بومی‌شده، صفحات عمومی، سرویس‌های نیازمند ورود و اپلیکیشن‌های تخصصی با هویت بصری مستقل را پوشش می‌دهد. بسته‌های فرهنگی US، IR و IQ نیز زبان و قالب محلی، تقویم، جهت نوشتار و فونت را به‌عنوان مفاهیم خود پلتفرم در نظر می‌گیرند.

‏یکپارچگی ظاهر هم به شانس واگذار نشده است. سیستم طراحی، **انضباط توکن‌های Fluent 2 را روی Tailwind و HeroUI** دنبال می‌کند؛ نه اینکه به Fluent React مهاجرت کرده باشد. قواعد مشترک تایپوگرافی، رنگ، فاصله، اجزا و تنظیمات ظاهر کمک می‌کنند صفحه‌هایی که جداگانه ساخته یا تولید می‌شوند، کم‌کم به چند محصول متفاوت تبدیل نشوند.

‏استانداردهای deep linking، ویرایشگرهای تودرتو و بسیاری از پنل‌ها و دیالوگ‌های فضای کاری را هم در بر می‌گیرند؛ می‌توان یک وضعیت مشخص را نشانه‌گذاری کرد و دوباره به آن برگشت. Workbookهای شخصی و اشتراکی، کارهای شبیه صفحه‌گسترده را پوشش می‌دهند. پوستهٔ برنامه نیز برای PWA آماده است و یک پوشش دسکتاپ اختیاری مبتنی بر Electron دارد.

‏همین جزئیات، فاصلهٔ بین «توسعه‌دهنده آن را ساخته» و «مردم می‌توانند هر روز از آن استفاده کنند» را کمتر می‌کنند.

## ‏۵. پلتفرم را توسعه بدهید، نه اینکه هسته را به برنامهٔ خودتان تبدیل کنید

‏پلتفرمی که قرار است چند بار استفاده شود، به مرزی روشن میان زیرساخت و رفتار اختصاصی کسب‌وکار نیاز دارد.

‏**Packages hub** در AppEndO امکان نصب، ساخت و خروجی گرفتن بسته‌های ZIP را برای افزونه‌ها و اپلیکیشن‌های تخصصی فراهم می‌کند. بسته‌های مرجع، الگوی ویجت، API، صفحه و اپلیکیشن تخصصی را نشان می‌دهند. Libraries نیز بسته‌های npm را در مخزن همان گره مدیریت می‌کند.

‏CMS و Remote Hubs بسته‌هایی موجود هستند؛ نه بهانه‌ای برای بزرگ کردن بی‌پایان هسته. CMS امکانات تولید و مدیریت محتوای تحریریه را فراهم می‌کند و Remote Hubs به‌صورت اختیاری ابزارهای File، SSH و RDP را اضافه می‌کند. نسخهٔ عمومی، فایل بسته‌های CMS و Remote Hubs را همراه دارد، نه همهٔ بسته‌های خصوصی یا برنامه‌ریزی‌شدهٔ هر حوزه را.

‏بازار مرکزی بسته‌ها و مجموعهٔ گسترده‌تر ماژول‌های آمادهٔ کسب‌وکار هنوز در نقشهٔ راه هستند. معیار ارزیابی باید چیزی باشد که امروز ارائه شده است؛ نه اینکه CRM، منابع انسانی یا تجارتِ آینده را جزو امکانات نصب‌شده حساب کنیم.

‏ایدهٔ معماری از همین حالا روشن است: **پلتفرم را دوباره استفاده کنید؛ تفاوت کسب‌وکارتان را در قالب بسته بسازید.**

## ‏۶. برای سال دوم طراحی کنید، نه فقط اسپرینت اول

‏نرم‌افزاری که قرار است بماند، باید برای این پرسش جواب داشته باشد: «وقتی این بخش تغییر کرد، چه می‌شود؟»

‏مرزبندی مستند قابلیت‌ها، قراردادهای مشترک، رابط‌های قابل استفادهٔ مجدد و روند برنامه‌ریزی AppEndO کمک می‌کنند پاسخ، کمتر وابسته به حافظهٔ کسی باشد که پیاده‌سازی اولیه را نوشته است. مدل تنظیمات نیز میان تنظیمات سراسری پلتفرم، تنظیمات محلی هر گره و تعریف‌های ساختاری مدل داده تفکیک قائل می‌شود.

‏در استقرار هم مرزها مشخص‌اند. یک گره می‌تواند هر سه نقش service، platform و worker را داشته باشد. در الگوی تفکیک‌شدهٔ مستند، چند پردازش service پشت یک متوازن‌کنندهٔ بار بیرونی قرار می‌گیرند، اما برای platform و worker همچنان یک نمونه در نظر گرفته شده است. انتخاب رهبر، هماهنگی توزیع‌شدهٔ workerها و به‌روزرسانی تدریجی خودکار، هنوز نباید به‌عنوان قابلیت کامل یک کلاستر معرفی شوند.

‏خودمیزبانی، اختیار زیرساخت و شیوهٔ استقرار را به تیم می‌دهد؛ مسئولیت بهره‌برداری را حذف نمی‌کند. مدیریت درست اسرار، از جمله کلید اصلی مخزن اعتبارنامه‌ها، TLS، تنظیم سیاست دسترسی، پایش و برنامهٔ بازیابی همچنان برای محیط عملیاتی ضروری‌اند.

‏این ادعا سالم‌تر از آن است که بگوییم «چون اسکرین‌شات سازمانی به نظر می‌رسد، پس آمادهٔ استفادهٔ سازمانی است». پلتفرم سازوکارها را فراهم می‌کند؛ تیم باید مناسب بودن آن‌ها را با نیازهای امنیتی و عملیاتی خودش بسنجد.

## ‏اولین برنامه را چطور می‌توان ساخت؟

‏یک سامانهٔ فرضی رسیدگی به درخواست خدمات در چند منطقه را در نظر بگیرید؛ این مثال، ادعای وجود یک بستهٔ آماده برای همین کار نیست:

1. ‏درخواست‌ها و رابطه‌هایشان را در Data Studio مدل کنید و Data APIهای لازم را منتشر کنید.
2. ‏مجوز فراخوانی بر اساس نقش و محدودهٔ رکوردها بر اساس سازمان و جغرافیا را تنظیم کنید.
3. ‏فهرست درخواست‌ها و فرم‌ها را با CRUD Set و Component Designer بسازید.
4. ‏اعتبارسنجی یا منطق اتصال اختصاصی را با Server Functions اضافه کنید.
5. ‏بررسی و تأیید را به یک گردش کار، همراه با وظایف انسانی و ارجاع به سطح بالاتر، تبدیل کنید.
6. ‏پرتال مشتری و فضای کاری کارشناس را روی همین پلتفرم ارائه کنید.
7. ‏رهگیری تاریخچهٔ رکورد و داشبوردی بر پایهٔ شاخص‌های مجاز اضافه کنید.
8. ‏بخش‌های قابل استفادهٔ مجدد را بسته‌بندی کنید و تغییرات را با ابزارهای موجود بررسی کنید.

‏طراحی منطق حوزه همچنان کار شماست. چیزی که حذف می‌شود، الزام به ساختن یک پلتفرم کامل پیش از تحویل اولین قابلیت واقعی است.

## ‏چه کسانی بهتر است AppEndO را جدی‌تر بررسی کنند؟

‏تیم‌های کوچکی که سیستم‌های جدی کسب‌وکار می‌سازند، سازمان‌هایی که باید پایگاه‌های دادهٔ موجود را به هم متصل کنند، مجریانی که اپلیکیشن‌های تخصصی تکرارپذیر تحویل می‌دهند و توسعه‌دهندگانی که کمک هوش مصنوعی را می‌خواهند، اما نه به قیمت از دست رفتن انسجام معماری.

‏اگر نیاز شما فقط یک سایت ایستا، یک سرویس بک‌اند مدیریت‌شده یا یک ERP کامل از روز اول است، احتمالاً گزینهٔ متناسب‌تری هم وجود دارد. نسخهٔ فعلی AppEndO هنوز در ابتدای مسیر است و پوشش آزمون مسیرهای پایگاه داده یکسان نیست: نصب اولیهٔ SQL Server و PostgreSQL توسط انسان آزمایش شده، SQLite آزمون ماشینی دارد و پوشش آزمون راهنمای نصب MySQL هنوز محدود است.

### ‏دربارهٔ مجوز، شفاف باشیم

‏کد AppEndO با **مجوز اختصاصی مبتنی بر Apache 2.0 و دارای شروط تکمیلی** منتشر می‌شود؛ نه Apache 2.0 استاندارد. بخش A اولویت حقوقی دارد: ایجاد و استفاده از fork فقط برای مشارکت در توسعهٔ AppEndO یا استفاده در شبکهٔ خصوصی مجاز است و میزبانی عمومی fork روی اینترنت ممنوع است. اجرای نسخهٔ رسمی برای کاربران نهایی، از جمله پرتال عمومی بدون نگهداری یک fork مستقل از کد پلتفرم، جداگانه در بخش A.4 مطرح شده است.

‏به همین دلیل، نباید آن را متن‌بازِ بدون این محدودیت‌ها یا متن‌باز به معنای مورد قبول OSI معرفی کرد. پیش از استفاده یا بازتوزیع، [متن کامل مجوز](../../LICENSE) را بخوانید. در دسترس بودن کد ارزشمند است؛ داشتن انتظار دقیق از حقوق استفاده هم به همان اندازه اهمیت دارد.

## ‏با یک نیاز واقعی امتحانش کنید، نه فقط با دیدن صفحهٔ معرفی

‏از [مخزن رسمی نسخهٔ عمومی](https://github.com/mirshahreza/AppEndO-Release) و راهنمای نصب آن شروع کنید. برای توسعه از روی کد، [README پروژه](../../README.md#installation) پیش‌نیاز Node.js 22، نصب وابستگی‌ها، اجرای `npm run dev` و راهنمای نصب مرورگری در `http://localhost:3000/install` را توضیح می‌دهد.

‏برای مسیر پیشنهادی SQL Server از راهنمای نصب استفاده کنید؛ `npm run setup` فقط راه‌اندازی اولیهٔ خط فرمان برای PostgreSQL است، نه نصب‌کنندهٔ عمومی همهٔ گزینه‌ها. پیش از ورود به محیط عملیاتی نیز مراحل مستند build، پیکربندی، تعویض امن اسرار و مقاوم‌سازی استقرار را انجام دهید.

‏بعد یک برش واقعی از برنامه بسازید: یک مجموعه‌دادهٔ واقعی، یک نقش با محدودهٔ مشخص، یک گردش کار و یک صفحهٔ مفید. این آزمون، خیلی بهتر از تیک زدن فهرست قابلیت‌ها نشان می‌دهد آیا پلتفرم به کار شما می‌آید یا نه.

‏اگر این رویکرد برایتان جذاب است، **به مخزن عمومی ستاره بدهید، نسخه را امتحان کنید و از مسیرهای رسمی پروژه در یک بهبود مشخص مشارکت کنید**؛ باگ قابل بازتولید، راهنمای روشن‌تر، یک بستهٔ قابل استفادهٔ مجدد یا تغییری کوچک و دقیق.

‏هوش مصنوعی تولید کد را آسان‌تر کرده است. مزیت بعدی، تبدیل آن کد به بخشی از سیستمی است که ارزش نگهداری داشته باشد.

‏**قدرت اسب را نگه دارید؛ افسار را اضافه کنید. خودِ برنامه را بسازید، نه دوباره تمام زیرساختش را.**
